# Introduction and Problem

The task in this project is to turn an owned VulnHub-style Linux OVA into a lower-resource Docker Compose replica, using a language-model agent, and then to say how complete that replica is. The agent does the work in stages: import the appliance, recover local administration when the guest password is unknown, repair end-of-life apt, inventory the guest, build one container, and score the container against the inventory. Completeness is configuration parity. It is not whether an attack chain succeeds. The score covers listeners, package version strings, users, sudoers, virtual hosts, web paths, the application database, cron, mail, and the application URL. Three facts stay visible even when those rows pass: archive or snapshot apt was required, the container shares the host kernel, and a process supervisor replaced the guest init system.

That conversion is a poor fit for an agent that only has the current conversation. The procedure is long, the guest is an old Debian system whose packages have left the active mirrors, and several local checks look successful while the replica is still wrong. A newer official image can install and answer HTTP while substituting Debian 9 and MariaDB for Debian 8 and MySQL. A database TCP check can succeed while PHP still uses the wrong Unix socket. Supervisor can report Sendmail as stopped, or as running, during the minute before ports 25 and 587 open. A stored application URL can be rewritten to a raw address even though the guest name still has to resolve. Boettiger (2015) framed the surrounding problem as reproducibility: an environment that ran once often cannot be executed again because the surrounding system has moved. Nüst et al. (2020) argued that a Dockerfile helps only when the base image and the versions are stated on purpose. Neither paper tells an agent when a substitution must stay out of the pass column.

The practical response is a set of skills: persistent procedural documents that the agent reads before it acts. Each skill states when it applies, what must already be true, which commands count, which checks verify the step, and when to stop. Haynes et al. (2009) showed that a checklist changes work of this shape by making the required actions and the pause points explicit. Yao et al. (2023) showed that a language model can interleave reasoning with tool use, and that the plan in that design is produced during the episode. A skill is the other arrangement. The procedure already exists, and the next agent is supposed to follow it instead of rediscovering it from the guest or from a finished Dockerfile. Jimenez et al. (2024) showed that success on realistic software tasks is still uncommon when success means a completed repair. The success definition here is the parity report, including the gaps the agent is forbidden to mark as passed.

The importance of the skills is that the conversion is meant to be repeated on other owned appliances. The chat that produced one replica does not travel with the next OVA. The Dockerfile records the settings that were chosen. It does not record the conditions under which a different setting would be a failed score. Without the skills, a later agent meets a working-looking container and the same traps. With the skills, it inherits the order of work, the stop conditions, and the evaluation template.

It reports the parity result after the procedure was applied, the substitutions an earlier replica still carried, and which decision rules live in the skills rather than in the finished container files. It does not report a second agent's wall-clock time, and it does not treat a script's file-search time as the speed of the model.
